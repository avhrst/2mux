# Довідник CLI

[English version](cli.md) · [Документація](README.uk.md) · [Посібник користувача](guide.uk.md)

## Контекст команд

Команди проєкту адресують сесію поточного робочого каталогу після розкриття символьних посилань. Виконуйте їх із кореня проєкту, використаного під час запуску, а не з підкаталогу. `help`, `version`, `send --queue DIR`, `status --queue DIR --json` і `watch --queue DIR` не потребують tmux чи пошуку сесії проєкту. Іншим командам потрібен tmux у `PATH`.

Ролі адресата й відправника чутливі до регістру: `worker` або `reviewer`. Параметри запуску не мають значень. Параметри надсилання записуються окремими аргументами перед адресатом і мають непорожні значення (крім прапорця `--steer`); форми на кшталт `--queue=DIR` не підтримуються. Порожнє значення `--queue` відхиляється замість переходу до пошуку сесії проєкту.

`start` і `stop` серіалізують зміни сесії того самого канонічного каталогу проєкту, очікуючи блокування життєвого циклу до десяти секунд. Простір блокувань не залежить від `TMPDIR` того, хто викликав команду. Інтерактивне підключення звільняє це блокування, тому інший термінал може підключитися знову чи зупинити сесію.

Успішні команди завершуються зі статусом `0`; помилка виводить `Error: ...` у stderr і завершується зі статусом `1`. За відсутності сесії `status`, `messages` і `stop` повідомляють, що 2mux не працює, та повертають успіх. `send` без адреси черги, `prompt`, `respawn` і `resolve` натомість повертають помилку.

## Запуск і підключення

```text
2mux
2mux start [--agents] [--detach] [--native|--codex-api|--claude-channel]
```

| Параметр | Поведінка |
| --- | --- |
| Без параметрів | Створити дві оболонки чи підключитися до наявної сесії; забезпечити роботу мосту. |
| `--agents` | У новій сесії запустити Codex як виконавця та Claude Code як рев’юера зі згенерованими інструкціями ролей; рев’юер працює з `--disallowedTools "Edit Write NotebookEdit"`. CLI `codex` і `claude` мають бути в `PATH`. У наявній сесії перевірити присутність агентів без заміни процесів. |
| `--detach` | Створити/використати сесію та забезпечити роботу мосту, потім показати її назву без підключення. Можна поєднувати з `--agents`. |

Інтерактивний запуск підключає через tmux; усередині клієнта tmux перемикає цей клієнт. Невідомі параметри запуску є помилкою. Наявна сесія має містити відповідну позначку каталогу й коректний приватний runtime-каталог. Відсутня чи завершена панель ролі спричиняє попередження, але не заважає підключенню; вона ніколи не замінюється автоматично. Щоб перезапустити її, використайте `2mux respawn ROLE`.

## Надсилання повідомлення

```text
2mux send [--queue DIR] [--from ROLE] [--kind KIND] [--reply-to ID] [--verdict VERDICT] [--steer] <worker|reviewer> <message|->
```

| Аргумент | Поведінка |
| --- | --- |
| Адресат | Обов’язковий: `worker` або `reviewer`. |
| Повідомлення | Рівно один аргумент оболонки або `-` для читання stdin. Текст із пробілами беріть у лапки. |
| `--queue DIR` | Адресувати наявну приватну чергу безпосередньо через файловий ввід/вивід. `DIR` і `DIR/messages` мають бути абсолютними каталогами поточного користувача Unix із правами `0700`. Цей шлях не шукає сесію tmux, не перевіряє панель адресата та не запускає/відновлює міст. Якщо черга не має справного мосту, повідомлення все одно ставиться в чергу, а в stderr виводиться попередження. |
| `--from ROLE` | Встановити відправника `worker` або `reviewer`. Це позначка повідомлення, а не автентифікація. |
| `--kind KIND` | `note` (звичайне повідомлення), `review_request` або `verdict`. Запит рев’ю має походити від ролі агента й адресуватися його партнеру; для команд агента використовуйте явний `--from`. |
| `--reply-to ID` | Точний ID наявного повідомлення від протилежної ролі. Обов’язковий для вердикту; необов’язковий для пов’язаної нотатки. Читайте отриманий заголовок, не вгадуйте останній запит. |
| `--verdict VERDICT` | `APPROVED` або `CORRECTIONS`, лише разом із `--kind verdict` та точним цільовим `review_request`. Кожен запит допускає один вердикт. |
| `--steer` | Спрямувати активний turn виконавця в сесії `--codex-api`. Інші адресати, ненативні сесії та сесії без активного turn відхиляються. |

Без `--queue` 2mux знаходить сесію поточного каталогу, перевіряє наявність панелі адресата та забезпечує роботу мосту. Відправник визначається за `TMUX_PANE`, якщо він збігається із зареєстрованою роллю; інакше це `user`. З `--queue` типовий відправник — `user`. `--from` замінює будь-яке типове значення; буквальне значення `user` цим параметром не приймається.

У разі успіху команда виводить `Queued message: ID`, а потім компактну картку ролі й прев’ю тексту. Це підтверджує збереження в черзі, а не доставку чи завершення завдання.

Правила повідомлень:

- Непорожній після усунення крайових пробілів текст, коректний UTF-8 і не більше 65 536 байтів, включно з байтами переведення рядків.
- Багаторядковий текст і табуляція дозволені. Інші керівні символи Unicode, зокрема carriage return та Escape, відхиляються; використовуйте закінчення рядків LF.
- Символи керування напрямком тексту відхиляються, як і будь-який рядок, перший непробільний текст якого — `[2mux` або `╭─ 2mux ·`, бо він міг би імітувати протокольний заголовок або картку ролі.
- Текст доставляється між заголовком, що містить ID повідомлення, відправника й адресата, і позначкою кінця `[2mux end of message ID]`.

Приклад оператора з каталогу проєкту:

```sh
2mux send reviewer - <<'MESSAGE'
Перевір запит виконавця на рев’ю.
Файли: docs/guide.uk.md, docs/cli.uk.md.
Перевірки: синтаксис команд і локальні посилання перевірено.
MESSAGE
```

Приклад агента з умовними шляхами (використовуйте точну команду з `2mux prompt worker`):

```sh
'/absolute/path/to/2mux' send --queue '/absolute/private/runtime' --from worker --kind review_request reviewer - <<'MESSAGE'
READY_FOR_REVIEW
Зміни, файли, точні команди й результати перевірок та відомі обмеження.
MESSAGE
```

Typed-запити й вердикти працюють через кожен транспорт, включно зі стандартною доставкою tmux. Запит фіксує весь Git scope, а не лише перелічені в тексті файли; наступні зміни можуть зробити вердикт невалідним. Спершу завершіть редагування й перевірки. Діагностична `--kind note` не є запитом рев’ю. У [процесі рев’ю](guide.uk.md#повідомлення-для-ревю) наведено точні команди вердиктів, Channel `ack`/`reply`, старі відповіді та повторне рев’ю після виправлень.

## Виведення інструкцій ролей

```text
2mux prompt <worker|reviewer>
```

Потребує запущеної сесії проєкту та коректних runtime-метаданих. Виводить інструкції ролі, абсолютний шлях до викликаного бінарного файла та адресу черги цієї сесії. Не запускає агента й не надсилає повідомлення. Виконавець чекає конкретного завдання й просить рев’ю через `READY_FOR_REVIEW`; рев’юер чекає повідомлення виконавця й відповідає один раз: `APPROVED` або нумерованими `CORRECTIONS`. Після перестворення сесії сформуйте нову інструкцію.

## Перегляд стану й квитанцій

```text
2mux status [--json] [--queue DIR]
2mux watch [--queue DIR]
2mux messages
```

Звичайний `status` виводить назву сесії, канонічний каталог проєкту, панель кожної ролі та результат перевірки готовності, стан мосту, кількість повідомлень за станами й runtime-каталог. `status --json` показує скорочені стани ролей, налаштування сесії, `transports` кожної ролі, лічильники квитанцій, помилки доставки та підключення Channel. Звичайний status також показує налаштований транспорт кожної ролі. `transports.worker: "tmux"` означає, що Codex API вимкнено, навіть якщо reviewer використовує native Channel. З `--queue DIR` команда читає приватний runtime безпосередньо; навіть без `--json` ця форма виводить JSON і не шукає панелі tmux. `watch` виводить змінені JSON-знімки раз на секунду. `messages` показує ID, відправника, адресата, стан і помилку кожного повідомлення, а потім шлях до каталогу `messages`; опції `--queue` немає, тому за відсутності контексту tmux переглядайте JSON-записи безпосередньо. Жодна з цих команд не запускає зупинений міст.

| Стан | Значення | Наступна дія |
| --- | --- | --- |
| `queued` | Збережене повідомлення очікує доставки. Помилка до вставлення може залишити його в черзі з текстом помилки. | Перевірте панель і міст; під час роботи мосту доставка з черги повторюється автоматично. |
| `sending` | Міст записав спробу доставки перед взаємодією з терміналом. | Короткий нормальний стан. Після переривання мосту відновлення змінює його на `uncertain`. |
| `delivered` | Вставлення й Enter завершилися успішно або оператор позначив квитанцію доставленою. | Окремо перевірте відповідь агента та результат завдання. |
| `uncertain` | Вставлення/надсилання могло відбутися або міст зупинився під час спроби. | Перевірте одержувача, потім явно визначте результат. Наступні повідомлення цьому адресату очікують. |

Стани мосту: `running (PID ...)`, `stopped`, `unresponsive` або `error: ...`. Працюючий міст також може показувати останню помилку черги/доставки, зокрема `waiting for pane ... to become idle` і `pane ... shows a confirmation dialog`. Міст вставляє текст лише в панель, екран якої не змінювався одну секунду, і затримує повідомлення, поки внизу екрана видно відомі фрази підтвердження. Це евристика; завершуйте власні діалоги CLI самостійно.

Якщо файл запису пошкоджено, `status` і `messages` усе одно показують коректні записи й називають кожен пошкоджений файл. Доставка для всіх адресатів призупиняється, доки файл не буде виправлено або видалено з каталогу `messages`.

## Визначення результату перерваної доставки

```text
2mux resolve <message-id> <delivered|retry>
```

Використовуйте повний ID з `messages` після перевірки агента-одержувача:

- `delivered` позначає запис доставленим і очищує помилку.
- `retry` змінює той самий запис на `queued` та очищує помилку. Працюючий міст зможе доставити його знову.

Змінювати можна лише записи `uncertain` або перервані `sending`. Невідомі ID та інші стани є помилками. Визначення результату серіалізується з доставкою мосту; зайнята черга може попросити повторити спробу. `resolve` не запускає зупинений міст. За потреби виконайте `2mux start --detach`. Не повторюйте доставку, поки її результат невідомий.

## Перезапуск завершеного агента

```text
2mux respawn <worker|reviewer>
```

Перезапускає CLI агента ролі (Codex для виконавця, Claude Code для рев’юера) з новими інструкціями ролі. Якщо зареєстрована панель завершилася, наприклад після виходу агента, агент запускається в цій самій панелі. Якщо панель видалено, поруч з іншою роллю створюється нова панель, яка реєструється явно. Жива панель ніколи не замінюється: спершу завершіть її процес. Повідомлення в черзі для ролі доставляються, щойно агент запрацює.

## Зупинення

```text
2mux stop
```

Спершу збережіть роботу в панелях. Команда зупиняє міст і сесію tmux поточного каталогу, завершуючи процеси панелей. Записи доставки залишаються, а їхній runtime-шлях виводиться. Нова сесія отримує новий runtime-каталог; стара черга не переноситься автоматично. Незалежні служби CLI агентів керують власним життєвим циклом.

Позначка належності каталогу має збігатися, щоб сесію можна було зупинити. Стару власну сесію без метаданих мосту також можна зупинити.

## Довідка й версія

```text
2mux help
2mux -h
2mux --help
2mux version
2mux -v
2mux --version
```

Альтернативні форми є командами верхнього рівня, а не параметрами запуску. Довідка й версія не приймають додаткових аргументів. Звичайне збирання показує `2mux dev`; змінна версії визначена в [version.go](../version.go).

`_bridge` — внутрішня точка входу дочірнього процесу. Запускайте чи відновлюйте його через `start`, а не прямим викликом.

## Native-параметри та кореляція

| Параметр | Значення |
| --- | --- |
| `start --codex-api` | У новій сесії запускає обох агентів, Codex використовує приватний app-server та remote TUI. |
| `start --claude-channel` | У новій сесії запускає обох агентів, Claude використовує MCP Channel. Research preview; development-channel і MCP consent підтверджує користувач. |
| `start --native` | Вмикає обидва експериментальні транспорти. |
| `send --kind KIND` | `note`, `review_request`, `verdict`. Review-запит і вердикт потребують `--from` ролі агента. |
| `send --reply-to ID` | Точний наявний ID від протилежної ролі; обов’язковий для вердикту. |
| `send --verdict VERDICT` | `APPROVED` або `CORRECTIONS`, лише з `--kind verdict`. Повторний чи застарілий вердикт відхиляється. |
| `send --steer` | Явний steer активного turn worker у `--codex-api` сесії. |
| `status --json [--queue DIR]` | JSON зі станами, лічильниками, конфігурацією та помилками доставки. Приватна queue-адреса працює без tmux. |
| `watch [--queue DIR]` | Виводить змінені JSON status snapshots щосекунди до Ctrl+C. |

| Стан | Значення |
| --- | --- |
| `submitted` | Запис у native-транспорт підтверджено, отримання агентом ще ні. |
| `accepted` | Codex user item має точний client ID або Claude викликав `ack`; hook може підтвердити legacy-повідомлення. |
| `rejected` | Review-вердикт невалідний або Git scope змінився до доставки; причина лишається у записі. Автоматичного повтору немає. |

Native-параметри консервативно перевіряють версію CLI. Перевірені версії: Codex 0.159.2 / 0.160.0 і Claude 2.1.289. Непідтримувані версії спричиняють помилку до створення нової сесії; native-транспорти не переходять на tmux. Наявна сесія та квитанції попередніх спроб зберігаються при невідповідності версії. Codex показує явне попередження, доки живий gate маршрутизації approvals G2 не підтверджено. Відсутній ack Channel через 90 секунд стає `uncertain`; пізній явний ack усе ще може підтвердити його.

`channel_connected` доводить тільки MCP-підключення. Перевіряйте реєстрацію `server:twomux` у native TUI. `starting`, `busy`, `idle`, `awaiting_approval`, `awaiting_input`, `exited`, `unknown` описують спостережений стан ролі, а не результат review. У legacy-режимі hooks спостерігають; свіжий approval затримує paste не довше 15 секунд, а pane/dialog перевірки діють і далі.

Legacy WORKER із Codex також показує `busy`, `idle` та підтримувані екрани `awaiting_approval` із `source: "codex-tui"` за явними елементами керування в зареєстрованій панелі. Ця евристика відображення працює без `--codex-api`; незнайомі компонування та діалоги вводу лишаються `unknown`, як і copy mode та невдала перевірка. Рядок статусу оновлюється раз на секунду. Наявна сесія отримає спостерігач після перезапуску bridge зі зібраним binary; сама збірка не замінює запущений bridge. Коли Codex API увімкнено, authoritative-джерелом лишаються його native-події.

Внутрішні `_hook` і `_channel` не є публічними командами оператора. Вони запускаються лише з приватних session settings/MCP-конфігурації. Приклади точних запитів/вердиктів і відновлення дивіться у [посібнику](guide.uk.md#експериментальна-native-комунікація).
