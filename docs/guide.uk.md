# Посібник користувача

[English version](guide.md) · [Документація](README.uk.md) · [Довідник CLI](cli.uk.md)

## Збирання та встановлення

Потрібні Linux або macOS із tmux і `ps`. Для збирання потрібен Go 1.22 або новіший, як зазначено в [go.mod](../go.mod). Для автоматичного запуску обох агентів спершу встановіть і налаштуйте CLI `codex` та `pi`; 2mux використовує їхні чинні облікові записи, моделі й дозволи. Зібраному бінарному файлу 2mux Go для роботи не потрібен.

Із каталогу вихідного коду 2mux зберіть програму в каталог, що належить вам:

```sh
mkdir -p "$HOME/.local/bin"
go build -o "$HOME/.local/bin/2mux" .
export PATH="$HOME/.local/bin:$PATH"
2mux version
2mux help
```

Додайте цей `export PATH` у конфігурацію оболонки, щоб налаштування діяло в нових терміналах. Звичайне збирання показує `2mux dev`. Можна також зібрати через `go build -o 2mux .` і викликати отриманий файл за абсолютним шляхом з іншого проєкту.

## Запуск завдання

Запускайте з проєкту, який мають змінювати агенти:

```sh
cd /path/to/project
2mux start --agents
```

У новій сесії Codex запускається в панелі WORKER ліворуч, pi — у панелі REVIEWER праворуч. Завершіть початкові діалоги довіри, входу чи дозволів кожного CLI, потім введіть конкретне завдання в Codex. Самі інструкції ролей наказують агентам чекати й не починають роботу над проєктом.

Обидва агенти використовують спільний каталог і робоче дерево. Виконавець реалізує завдання та надсилає рев’юеру підсумок, змінені файли й результати перевірок. Рев’юер отримує інструкцію перевірити файли та доречні тести без редагування файлів проєкту й повернути `CORRECTIONS` або `APPROVED`. Виконавець застосовує конкретні виправлення та просить повторне рев’ю, завершуючи цикл після схвалення. Це інструкції агентам, а не розмежування доступу до файлової системи.

Завдання можна передати з іншого термінала в каталозі проєкту:

```sh
2mux send worker 'Створи документацію проєкту з перевіреними прикладами команд.'
```

Квитанція означає, що завдання потрапило в чергу. Завершення визначайте за відповіддю виконавця та фактичними змінами.

## Повідомлення для рев’ю

Агенти мають використовувати точну команду надсилання зі своєї інструкції ролі. Вона містить абсолютний шлях до програми, адресу приватної черги сесії та явного відправника, тому працює, коли shell-інструмент агента фільтрує `TMUX` або `PATH`.

Оператор у каталозі проєкту може застосувати коротку форму:

```sh
2mux send reviewer - <<'MESSAGE'
Готово до рев’ю.
Підсумок: додано документацію встановлення та CLI.
Файли: README.uk.md, docs/guide.uk.md, docs/cli.uk.md.
Перевірка: приклади команд звірено з довідкою CLI.
Перевір файли та поверни APPROVED або конкретні CORRECTIONS.
MESSAGE
```

Лапки навколо роздільника heredoc зберігають буквальний текст, зокрема лапки, зворотні апострофи та знаки долара. Саме виведення маркерів рев’ю не надсилає повідомлення. Кожен виклик `send` створює окреме повідомлення; повторні запити мають різні ID.

## Від’єднання та повернення

Зі стандартним префіксом tmux натисніть `Ctrl+B`, потім `D`, щоб від’єднатися. Агенти й міст продовжують роботу. Із того самого каталогу проєкту виконайте:

```sh
2mux
```

Команда підключається до наявної сесії та запускає міст, якщо він зупинився. Усередині клієнта tmux вона перемикає його на потрібну сесію. Ролі визначаються збереженими ID панелей, тому перестановка панелей чи нове вікно не змінюють адресатів.

Для запуску без підключення:

```sh
2mux start --agents --detach
2mux status
```

Підключіться пізніше через `2mux`, щоб завершити початкові діалоги агентів. Запуск без підключення не обробляє ці діалоги замість вас.

## Ручний запуск агентів

`2mux start` створює дві оболонки з працюючим мостом. У панелі WORKER:

```sh
exec codex "$(2mux prompt worker)"
```

У панелі REVIEWER:

```sh
exec pi --append-system-prompt "$(2mux prompt reviewer)"
```

Виконуйте ці команди з каталогу проєкту, коли `2mux` доступний у `PATH`. `exec` замінює оболонку, щоб повідомлення після завершення агента не потрапило в цю оболонку. Після перестворення сесії сформуйте інструкції ролей заново: адреса черги змінюється.

У наявній сесії `start --agents` перевіряє присутність агентів і не замінює поточні процеси. Якщо в панелях ще оболонки, запустіть агентів вручну, як вище. Якщо агент завершився й залишив завершену панель або його панель видалено, виконайте `2mux respawn worker` чи `2mux respawn reviewer`; повідомлення в черзі для цієї ролі доставляться, щойно агент запрацює.

## Діагностика доставки

Почніть із команд:

```sh
2mux status
2mux messages
```

`status` показує зареєстровані панелі, розпізнаних агентів, стан мосту, кількість повідомлень і runtime-каталог. `messages` перелічує ID, адресатів, стани, помилки та каталог записів повідомлень. Тексти повідомлень команда не виводить; вони містяться в окремих JSON-записах.

| Симптом | Що зробити |
| --- | --- |
| `tmux ... not found in PATH` | Зробіть tmux доступним оболонці запуску та повторіть команду. |
| Потрібен `codex` або `pi` | Зробіть обидва налаштовані CLI доступними в `PATH` перед `start --agents`. |
| Панель очікує інтерактивного агента | Завершіть ручний запуск або перевірте активну програму. Повідомлення очікують, поки в панелі оболонка чи нерозпізнаний процес. |
| Панель у режимі копіювання чи з вимкненим вводом | Вийдіть із режиму копіювання або відновіть ввід панелі, потім перевірте чергу. |
| Міст зупинено, або `send` агента виводить `Warning: 2mux bridge is ...` | Виконайте `2mux start --detach` із того самого каталогу, щоб перезапустити його без підключення. Після цього повідомлення з черги буде доставлено. |
| Міст заблоковано, але він не відповідає | Перевірте `status`, `health.json` і `bridge.log` у показаному runtime-каталозі. Запуск іншого мосту не обходить чинне блокування. |
| Зареєстрована панель відсутня/завершена | Збережіть роботу, потім виконайте `2mux respawn ROLE`, щоб перезапустити агента. Тим часом `2mux` усе одно підключається. |
| Панель показує діалог підтвердження | Дайте відповідь у діалозі агента самостійно; затримані повідомлення надійдуть після його закриття. |
| Очікування, доки панель стане спокійною | Нормально, поки агент виводить текст; доставка відбудеться після секунди спокою. |
| `status` показує пошкоджені записи | Перегляньте названий файл у каталозі `messages`, потім виправте або видаліть його; доти доставку призупинено. |
| Сесія не має runtime-каталогу мосту | Збережіть роботу, потім виконайте `2mux stop` і створіть нову сесію. |
| Однойменна сесія не належить 2mux | Окремо перевірте цю сесію tmux; 2mux відмовляється підключатися до неї чи зупиняти її. |
| Повідомлення має стан `uncertain` | Перевірте агента-одержувача перед зміною квитанції, як описано нижче. |

Міст перевіряє розпізнаваного активного агента, спокійний екран і відомі фрази підтвердження, а не готовність кожного діалогу CLI прийняти запит. Завершуйте власні підтвердження CLI самостійно й уникайте введення в панель одержувача під час надсилання повідомлення.

## Визначення результату невизначеної доставки

`delivered` означає, що міст вставив повідомлення й надіслав Enter у термінал. Це не підтверджує, що модель прочитала або виконала запит. Якщо надсилання могло початися до помилки чи аварії, міст позначає повідомлення `uncertain` і призупиняє наступні повідомлення цьому адресату.

1. Знайдіть ID і помилку через `2mux messages`.
2. Перевірте панель одержувача та відповідь агента на цей ID повідомлення.
3. Якщо надсилання підтверджено, замініть умовний ID і позначте його доставленим:

   ```sh
   2mux resolve MESSAGE_ID delivered
   ```

4. Якщо ви встановили, що надсилання не відбулося, поверніть той самий запис у чергу:

   ```sh
   2mux resolve MESSAGE_ID retry
   ```

Залиште квитанцію невизначеною, поки результат невідомий. Повтор може продублювати вже надісланий запит. Інший адресат може продовжувати отримувати свої повідомлення.

## Зупинення та збереження записів

Збережіть роботу в обох панелях, потім виконайте з каталогу проєкту:

```sh
2mux stop
```

Команда зупиняє міст і сесію tmux, завершуючи процеси панелей. Незалежні служби CLI керують власним життєвим циклом. Показаний runtime-каталог залишається для перегляду чи ручного видалення записів. Збережіть потрібні квитанції до очищення тимчасового сховища операційною системою.

Записи містять текст повідомлень. Права приватних каталогів і файлів обмежують доступ інших користувачів Unix; обидва агенти все одно працюють під вашим обліковим записом і зі спільним проєктом. 2mux не збирає транскрипти терміналів, облікові дані чи телеметрію. Після створення нової сесії використовуйте нові інструкції ролей та адресу черги.
