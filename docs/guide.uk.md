# Посібник користувача

[English version](guide.md) · [Документація](README.uk.md) · [Довідник CLI](cli.uk.md)

## Збирання та встановлення

Потрібні Linux або macOS із tmux і `ps`. Для збирання потрібен Go 1.22 або новіший, як зазначено в [go.mod](../go.mod). Для автоматичного запуску обох агентів спершу встановіть і налаштуйте CLI `codex` та `claude`; 2mux використовує їхні чинні облікові записи, моделі й дозволи. Зібраному бінарному файлу 2mux Go для роботи не потрібен.

Із каталогу вихідного коду 2mux зберіть програму в каталог, що належить вам:

```sh
mkdir -p "$HOME/.local/bin"
go build -o "$HOME/.local/bin/2mux" .
export PATH="$HOME/.local/bin:$PATH"
2mux version
2mux help
```

Додайте цей `export PATH` у конфігурацію оболонки, щоб налаштування діяло в нових терміналах. Звичайне збирання показує `2mux dev`. Можна також зібрати через `go build -o 2mux .` і викликати отриманий файл за абсолютним шляхом з іншого проєкту.

## Запуск завдання

Запускайте з проєкту, який мають змінювати агенти:

```sh
cd /path/to/project
2mux start --agents
```

У новій сесії Codex запускається в панелі WORKER ліворуч, Claude Code — у панелі REVIEWER праворуч. Завершіть початкові діалоги довіри, входу чи дозволів кожного CLI, потім введіть конкретне завдання в Codex. Самі інструкції ролей наказують агентам чекати й не починають роботу над проєктом.

Обидва агенти використовують спільний каталог і робоче дерево. Виконавець реалізує завдання та надсилає рев’юеру повідомлення, що починається з `READY_FOR_REVIEW`: підсумок, змінені файли, точні команди перевірки з результатами та відкриті питання. Рев’юер отримує інструкцію переглянути `git status` і diff, зокрема невідстежувані файли, і може запускати перевірки чи тести лише для читання, але ніколи не редагує файли й не змінює стан git. Він відповідає один раз на кожен запит: `APPROVED` з однорядковим обґрунтуванням або `CORRECTIONS` у вигляді нумерованого списку з `file:line`, проблемою та очікуваним виправленням. Під час повторного рев’ю він спершу перевіряє попередні виправлення. Виконавець застосовує виправлення та просить повторне рев’ю, зупиняється після схвалення, не відповідаючи на нього, і не робить commit чи push без прохання. Це інструкції агентам, а не розмежування доступу до файлової системи; керований і ручний запуск рев’юера додатково забороняють інструменти Claude Code `Edit`, `Write` і `NotebookEdit`, а команди оболонки й далі підлягають звичайним дозволам Claude Code.

Завдання можна передати з іншого термінала в каталозі проєкту:

```sh
2mux send worker 'Створи документацію проєкту з перевіреними прикладами команд.'
```

Квитанція означає, що завдання потрапило в чергу. Завершення визначайте за відповіддю виконавця та фактичними змінами.

## Повідомлення для рев’ю

Агенти мають використовувати точну команду надсилання зі своєї інструкції ролі. Вона містить абсолютний шлях до програми, адресу приватної черги сесії та явного відправника, тому працює, коли shell-інструмент агента фільтрує `TMUX` або `PATH`.

Запит виконавця на рев’ю використовує `--kind review_request` і в tmux, і в native-режимі. Збережіть згенеровані абсолютний шлях до програми та адресу черги; нижче наведено умовні шляхи:

```sh
'/absolute/path/to/2mux' send --queue '/absolute/private/runtime' --from worker --kind review_request reviewer - <<'MESSAGE'
READY_FOR_REVIEW
Підсумок: додано документацію встановлення та CLI.
Файли: README.uk.md, docs/guide.uk.md, docs/cli.uk.md.
Перевірка: приклади команд звірено з довідкою CLI.
Перевір файли та поверни APPROVED або конкретні CORRECTIONS для цього точного запиту.
MESSAGE
```

Для запиту, отриманого через tmux, рев’юер читає ID із заголовка повідомлення та надсилає один typed-вердикт, зберігаючи власні згенеровані шлях до програми й адресу черги:

```sh
'/absolute/path/to/2mux' send --queue '/absolute/private/runtime' --from reviewer --kind verdict --reply-to REQUEST_ID --verdict APPROVED worker 'APPROVED: checks passed'
```

Замініть `REQUEST_ID` точним ID із заголовка. Для виправлень використовуйте `--verdict CORRECTIONS` і текст, що починається з `CORRECTIONS` та перелічує конкретні зауваження. Для native Claude Channel рев’юер використовує інструменти: спершу `ack(message_id)`, потім `reply(reply_to, text, verdict)` із тим самим точним ID. Старий нетипізований запит отримує звичайну відповідь без прапорців вердикту. Нагадування оператора використовують звичайну команду `2mux send reviewer 'Перевір запит виконавця.'`; вона не створює typed-запиту на рев’ю.

Кореляція typed-рев’ю діє для кожного транспорту. Завершіть редагування й перевірки перед надсиланням: scope охоплює все робоче дерево Git, тому навіть зміна стороннього файла може зробити вердикт невалідним. На кожен запит допускається один вердикт; після `CORRECTIONS` виправте зауваження, повторіть перевірки та надішліть новий запит. Після `APPROVED` зупиніться, не відповідаючи на нього. Схвалення рев’ю не дає дозволу на виконання інструментів, commit чи push.

Лапки навколо роздільника heredoc зберігають буквальний текст, зокрема лапки, зворотні апострофи та знаки долара. Саме виведення маркерів рев’ю не надсилає повідомлення. Кожен виклик `send` створює окреме повідомлення; повторні запити мають різні ID.

## Перевірка зв’язку між агентами

Після завершення стартових діалогів надішліть одну діагностичну нотатку згенерованою командою виконавця:

```sh
'/absolute/path/to/2mux' send --queue '/absolute/private/runtime' --from worker --kind note reviewer - <<'MESSAGE'
COMMUNICATION_CHECK
Відповідай один раз COMMUNICATION_OK на точний ID цього повідомлення; вердикт рев’ю не потрібен.
Для Claude Channel спочатку виклич ack, потім reply без вердикту.
MESSAGE
```

Перегляньте `2mux status --json --queue '/absolute/private/runtime'` та відповідні файли `messages/ID.json`. Відповідь рев’юера має походити від `reviewer`, адресуватися `worker` і містити точний ID діагностичного запиту в `reply_to`. Через tmux рев’юер може додати `--kind note --reply-to MESSAGE_ID` до своєї згенерованої команди; через Channel він використовує `reply` без `verdict`. Сама квитанція `queued` або `channel_connected: true` не завершує перевірку. Також підтвердьте фактичну відповідь у панелі виконавця.

У змішаній сесії `--claude-channel` вихідна нотатка може отримати `accepted` через Channel, поки відповідь чекає, щоб tmux-панель виконавця стала спокійною. `worker: unknown` може означати, що native-спостерігач стану не увімкнений. Дайте виконавцю завершити поточний вивід і перевірте наявні квитанції перед надсиланням ще однієї нотатки. Ця діагностика перевіряє доставку й кореляцію; наступне рев’ю потребує власного `review_request` та вердикту. Вона не перевіряє окремий транспорт Codex API або маршрутизацію дозволів інструментів.

## Видима комунікація в CLI

Вхідні повідомлення починаються з компактної картки з відправником, адресатом і типом повідомлення. Точні ID квитанцій та кінцева позначка залишаються під карткою для кореляції. Результати вихідного `send` та Claude Channel `ack`/`reply` показують таке саме оформлення зі станом `queued` або `accepted` і прев’ю до восьми рядків та 480 символів. Повний текст зберігається в черзі й доставляється без скорочень:

```text
╭─ 2mux · WORKER → REVIEWER
│ REVIEW REQUEST · queued
╰──────────────────────────────────────
READY_FOR_REVIEW
Підсумок: зробити обмін видимим у CLI обох агентів.
Перевірка: транспорт і оформлення перевірено.
```

Інструкції ролей і Channel просять кожного агента показувати короткий запис у звичайній розмові під час отримання повідомлення та перед надсиланням запиту чи вердикту. Native CLI самі визначають згортання повідомлень і результатів інструментів; запис у розмові зберігає обмін видимим без відкриття цих подробиць. Схвалення повідомляється користувачеві один раз і не отримує підтвердження у відповідь партнеру.

Заголовки панелей використовують блакитний для WORKER/Codex і фіолетовий для REVIEWER/Claude. Вони показують напрямок, стан квитанції та тип останнього пов’язаного повідомлення навіть під час роботи агента. У панелях вужчих за 60 колонок назви ролей скорочуються, а партнери позначаються `W`, `R` або `U`. Наприклад, `WORKER │ ←R · queued · approved` означає, що останній вердикт рев’юера ще в черзі, а не що доставка виконавцю завершилася. Заголовок описує останнє повідомлення, а не схвалення поточного робочого дерева. Порожня панель показує, кого очікує; пошкоджена черга показує `Queue needs attention`. Завдання заголовка лише читає дані, не починає turn моделі й не містить текстів повідомлень.

Після збирання виконайте `2mux start --detach`, щоб застосувати заголовки до наявної пари без перезапуску агентів. Оновлення заголовків використовує наявний інтервал оновлення статусу tmux. Уже запущені процеси мосту та Channel зберігають форматування, завантажене при запуску; нові вхідні картки й квитанції native-інструментів діятимуть після наступного запуску цих процесів. Нові інструкції ролей містять правило видимого обміну; наявному агенту надішліть нотатку з проханням показувати повідомлення партнера у звичайній розмові.

## Від’єднання та повернення

Зі стандартним префіксом tmux натисніть `Ctrl+B`, потім `D`, щоб від’єднатися. Агенти й міст продовжують роботу. Із того самого каталогу проєкту виконайте:

```sh
2mux
```

Команда підключається до наявної сесії та запускає міст, якщо він зупинився. Усередині клієнта tmux вона перемикає його на потрібну сесію. Ролі визначаються збереженими ID панелей, тому перестановка панелей чи нове вікно не змінюють адресатів.

Для запуску без підключення:

```sh
2mux start --agents --detach
2mux status
```

Підключіться пізніше через `2mux`, щоб завершити початкові діалоги агентів. Запуск без підключення не обробляє ці діалоги замість вас.

## Ручний запуск агентів

`2mux start` створює дві оболонки з працюючим мостом. У панелі WORKER:

```sh
exec codex "$(2mux prompt worker)"
```

У панелі REVIEWER:

```sh
exec claude --append-system-prompt "$(2mux prompt reviewer)" --disallowedTools "Edit Write NotebookEdit"
```

Виконуйте ці команди з каталогу проєкту, коли `2mux` доступний у `PATH`. `exec` замінює оболонку, щоб повідомлення після завершення агента не потрапило в цю оболонку. Після перестворення сесії сформуйте інструкції ролей заново: адреса черги змінюється.

У наявній сесії `start --agents` перевіряє присутність агентів і не замінює поточні процеси. Якщо в панелях ще оболонки, запустіть агентів вручну, як вище. Якщо агент завершився й залишив завершену панель або його панель видалено, виконайте `2mux respawn worker` чи `2mux respawn reviewer`; повідомлення в черзі для цієї ролі доставляться, щойно агент запрацює.

## Діагностика доставки

Почніть із команд:

```sh
2mux status
2mux messages
```

`status` показує зареєстровані панелі, розпізнаних агентів, стан мосту, кількість повідомлень і runtime-каталог. `messages` перелічує ID, адресатів, стани, помилки та каталог записів повідомлень. Тексти повідомлень команда не виводить; вони містяться в окремих JSON-записах.

| Симптом | Що зробити |
| --- | --- |
| `tmux ... not found in PATH` | Зробіть tmux доступним оболонці запуску та повторіть команду. |
| Потрібен `codex` або `claude` | Зробіть обидва налаштовані CLI доступними в `PATH` перед `start --agents`. |
| Панель очікує інтерактивного агента | Завершіть ручний запуск або перевірте активну програму. Повідомлення очікують, поки в панелі оболонка чи нерозпізнаний процес. |
| Панель у режимі копіювання чи з вимкненим вводом | Вийдіть із режиму копіювання або відновіть ввід панелі, потім перевірте чергу. |
| Міст зупинено, або `send` агента виводить `Warning: 2mux bridge is ...` | Виконайте `2mux start --detach` із того самого каталогу, щоб перезапустити його без підключення. Після цього повідомлення з черги буде доставлено. |
| Міст заблоковано, але він не відповідає | Перевірте `status`, `health.json` і `bridge.log` у показаному runtime-каталозі. Запуск іншого мосту не обходить чинне блокування. |
| Зареєстрована панель відсутня/завершена | Збережіть роботу, потім виконайте `2mux respawn ROLE`, щоб перезапустити агента. Тим часом `2mux` усе одно підключається. |
| Панель показує діалог підтвердження | Дайте відповідь у діалозі агента самостійно; затримані повідомлення надійдуть після його закриття. |
| Очікування, доки панель стане спокійною | Нормально, поки агент виводить текст; доставка відбудеться після секунди спокою. |
| `status` показує пошкоджені записи | Перегляньте названий файл у каталозі `messages`, потім виправте або видаліть його; доти доставку призупинено. |
| Сесія не має runtime-каталогу мосту | Збережіть роботу, потім виконайте `2mux stop` і створіть нову сесію. |
| Однойменна сесія не належить 2mux | Окремо перевірте цю сесію tmux; 2mux відмовляється підключатися до неї чи зупиняти її. |
| Повідомлення має стан `uncertain` | Перевірте агента-одержувача перед зміною квитанції, як описано нижче. |

Міст перевіряє розпізнаваного активного агента, спокійний екран і відомі фрази підтвердження, а не готовність кожного діалогу CLI прийняти запит. Завершуйте власні підтвердження CLI самостійно й уникайте введення в панель одержувача під час надсилання повідомлення.

## Визначення результату невизначеної доставки

`delivered` означає, що міст вставив повідомлення й надіслав Enter у термінал. Це не підтверджує, що модель прочитала або виконала запит. Якщо надсилання могло початися до помилки чи аварії, міст позначає повідомлення `uncertain` і призупиняє наступні повідомлення цьому адресату.

1. Знайдіть ID і помилку через `2mux messages`.
2. Перевірте панель одержувача та відповідь агента на цей ID повідомлення.
3. Якщо надсилання підтверджено, замініть умовний ID і позначте його доставленим:

   ```sh
   2mux resolve MESSAGE_ID delivered
   ```

4. Якщо ви встановили, що надсилання не відбулося, поверніть той самий запис у чергу:

   ```sh
   2mux resolve MESSAGE_ID retry
   ```

Залиште квитанцію невизначеною, поки результат невідомий. Повтор може продублювати вже надісланий запит. Інший адресат може продовжувати отримувати свої повідомлення.

## Зупинення та збереження записів

Збережіть роботу в обох панелях, потім виконайте з каталогу проєкту:

```sh
2mux stop
```

Команда зупиняє міст і сесію tmux, завершуючи процеси панелей. Незалежні служби CLI керують власним життєвим циклом. Показаний runtime-каталог залишається для перегляду чи ручного видалення записів. Збережіть потрібні квитанції до очищення тимчасового сховища операційною системою.

Записи містять текст повідомлень. Права приватних каталогів і файлів обмежують доступ інших користувачів Unix; обидва агенти все одно працюють під вашим обліковим записом і зі спільним проєктом. 2mux не збирає транскрипти терміналів, облікові дані чи телеметрію. Після створення нової сесії використовуйте нові інструкції ролей та адресу черги.

## Експериментальна native-комунікація

Збережіть роботу перед заміною наявної сесії. Із того самого кореня проєкту створіть нову сесію через `2mux start --native` або використайте `--codex-api` / `--claude-channel` окремо. Кожен прапорець передбачає `--agents`. Повторне підключення не змінює транспортів і не перериває агента. Backend Codex працює в окремому вікні сесії `2mux-api`; зупинка сесії зупиняє цей приватний backend. Спільні daemon Codex не зачіпаються.

Завершіть стартові діалоги Codex у worker-панелі. `--dangerously-load-development-channels server:twomux` у Claude показує повноекранну згоду при кожному запуску. Власноруч підтвердьте її та згоду на MCP, потім перевірте, що стартове повідомлення Claude перелічує `server:twomux` як Channel. Якщо акаунт, provider або політика організації відхиляють Channels, не надсилайте повідомлень: збережіть роботу й перестворіть сесію без `--claude-channel`. Саме MCP-підключення у статусі 2mux не перевіряє цю політику.

Введіть задачу в worker-панелі й використовуйте описаний вище [обмін повідомленнями для рев’ю](#повідомлення-для-ревю). Виконавець і далі надсилає повідомлення у приватну чергу; інструкції native Claude Channel вимагають від рев’юера спочатку викликати `ack(message_id)`, потім `reply(reply_to, text, verdict)` для точного запиту. ID ніколи не вгадується за останнім повідомленням.

Git scope review поєднує HEAD, staged/unstaged diff та неігноровані untracked-шляхи і вміст. Зміни після запиту роблять вердикт невалідним при додаванні в чергу й повторно перед доставкою. Пов’язані записи запитів/відповідей зберігаються для перевірки. Поза Git-репозиторієм або до першого commit scope відсутній; перевірки точного ID та ролей діють.

Використовуйте `2mux status --json` або `2mux watch` для станів ролей, лічильників і `transports` кожної ролі. Повний native-режим потребує `transports.worker: "codex"` і `transports.reviewer: "claude-channel"`; змішана пара з worker `tmux` не є повним native-режимом. Подання в native-чергу швидке, але звичайний queued input очікує межі turn; `--steer` явно призначений для вводу в активний turn. `starting` не є idle; очікування дозволу чи введення користувача відокремлені від review-вердиктів. Session hooks Claude спостерігають busy/idle/approval/exited. Події Codex фільтруються за точним thread сесії. Status line сесії показує обидві ролі.

При перепідключенні Codex читає наявну чергу й сторінки історії user items. Точний ID у черзі лишається `submitted`; точний client ID user item стає `accepted`; відсутній ID стає `uncertain`. Перезапуск Claude Channel не доводить отримання непідтвердженого повідомлення, тому воно стає `uncertain`, а наступні чекають на явний ack або рішення оператора. Після спроби немає автоматичного повтору через paste чи інший транспорт. Збої native видимі; `2mux start` перепідключається до наявного backend, а `respawn` відновлює збережену сесію агента після завершення його панелі.

Новий потік виконавця Codex отримує назву до закриття bootstrap-з’єднання: це зберігає rollout без модельного ходу. Якщо Codex повертає `no rollout found` (`-32600`), bootstrap і міст очищують збережений ID перед створенням і записом нового потоку. Інші помилки відновлення та невідповідності thread/CWD зупиняють відновлення без заміни потоку. Після завершення виконавця через відсутній rollout виконайте `2mux respawn worker`: preflight виправить збережений потік до запуску TUI.

`resolve ID delivered` — твердження оператора, що подання відбулося, а не native receipt. `resolve ID retry` явно дозволяє ще одну спробу через той самий зафіксований транспорт. Спочатку перевірте native-чергу/історію та отримувача. Непідтримувана native-версія CLI повертає помилку без зміни транспортів або повтору квитанцій. Якщо потрібен legacy-транспорт, виберіть його явно під час створення нової сесії.

Непідтверджене подання Channel стає `uncertain` через 90 секунд навіть без перезапуску; пізній ack може підтвердити його. Застарілий вердикт у черзі стає кінцевим `rejected` із причиною, без автоматичної повторної перевірки чи доставки.
