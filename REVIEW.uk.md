# Рев’ю 2mux — 30.09.2026

[English version](REVIEW.md)

Перевірено весь початковий код, запуск і належність сесій, ролі панелей, транспорт повідомлень, відновлення, CLI, тести та документацію. Основна причина несправності: початкова версія відкривала дві оболонки, а функції мосту ніде не викликалися. Автоматичний обмін, якого очікував користувач, не був реалізований.

## Знайдено та виправлено

| Пріоритет | Проблема та наслідок | Реалізоване виправлення |
| --- | --- | --- |
| P1 | `start` лише підключав tmux; агенти не отримували повідомлень один від одного. | Фоновий міст запускається автоматично; `send` записує повідомлення, міст доставляє їх навіть без підключеного клієнта. Додано `start --agents` для Codex + pi з інструкціями ролей. |
| P1 | Живий тест виявив фільтрацію `TMUX`/`PATH` shell-інструментом Codex: короткий `send` не знаходив потрібної сесії. | Інструкції містять абсолютний шлях, явний `--queue DIR` і `--from ROLE`. Цей шлях надсилання працює лише з файловою системою та не потребує tmux у shell-інструменті агента. |
| P1 | Не було черги чи квитанцій; наявні допоміжні функції захоплення екрана не забезпечували відновлення або захисту від повторів. | Атомарні JSON-записи, унікальні ID, порядок для кожного адресата, блокування процесів, стани `queued`, `sending`, `delivered`, `uncertain`. Завершені доставки не повторюються після перезапуску. |
| P1 | Невизначений результат вставлення/підтвердження міг призвести до повторного надсилання. | `uncertain` блокує подальші повідомлення цьому адресату до явного `resolve`. Після аварії записи `sending` також стають невизначеними. |
| P1 | Початковий невикористаний `sendText` надсилав багаторядковий текст як натискання клавіш, без перевірки процесу. При підключенні такого коду повідомлення могло потрапити в оболонку. | Bracketed paste одним буфером, перевірки foreground-процесу, завершених панелей, режиму копіювання та вимкненого вводу. Керівні символи відхиляються. Керований запуск виконує CLI напряму; ручні приклади використовують `exec`. |
| P2 | Ролі та статус визначалися за положенням/кількістю панелей; активне додаткове вікно могло змінити результат. | Ролі зберігаються за ID панелей, перевіряються в усій сесії й не переходять автоматично іншій панелі. Перестановка та нове вікно не змінюють адресата. |
| P2 | Пряме використання exact-target у командах tmux для вікон виявилося несумісним без роздільника `:`. На macOS `ps comm` обрізав шлях; pi також змінює назву процесу. | Сесії та вікна адресуються відповідно до типу target. Визначення агентів використовує `ucomm`, foreground-стан, назву pi та перевірені варіанти запуску через Node/симлінк. |
| P2 | Не було перевірки автоматичного сценарію, стану мосту чи захисту від одночасних запусків. | Додано health-записи, блокування запуску/черги, обмежені batch і таймаути команд, `status`, `messages`, `resolve`, unit-, integration- та native smoke-тести. |

Основні зміни: [main.go](main.go), [bridge.go](bridge.go), [queue.go](queue.go), [tmux.go](tmux.go). Українська та англійська [документація](README.uk.md) узгоджені.

## Перевірено

- `go test -race ./...` і `go vet ./...` пройшли.
- `TWOMUX_INTEGRATION=1 TWOMUX_NATIVE_SMOKE=1 go test -race -v ./...` пройшов. Фікстури перевірили вісім доставок: повний цикл із виправленнями та схваленням, UTF-8, перестановку панелей, додаткове вікно, одночасне відновлення мосту, відсутність повторів, режим копіювання, вимкнений ввід, оболонку замість агента, відсутню роль і захист чужої сесії.
- Окремий regression-тест підтвердив надсилання через явну чергу з порожніми `TMUX`/`TMUX_PANE` і `PATH` без tmux.
- Native smoke-тест розпізнав встановлені Codex і pi без надсилання запиту моделі.
- Живий тест зі справжніми Codex і pi пройшов: `hello.txt` містив рівно `2mux automatic review works` та один LF, 28 байтів. Codex автоматично надіслав запит; pi самостійно перевірив байти та повернув `APPROVED`; Codex отримав відповідь і підтвердив завершення. Квитанції та точний результат збережено у [live-review-20260930.json](validation/live-review-20260930.json). Було сім окремо створених повідомлень із різними ID, кожне доставлено один раз; повторні запити авторства агентів не є повторною доставкою одного запису.
- Зібрано локальний бінарний файл `2mux` для macOS arm64 та виконано cross-build для Linux amd64. Тестове середовище: Go 1.27.1, tmux 3.6a, Codex 0.159.2, pi 0.99.1.
- Тимчасові тестові сесії, проєкт і runtime-каталоги прибрано. Чужі сесії tmux не використовувалися.

## Межі результату

`delivered` підтверджує надсилання в термінал. Якість відповіді, виконання команд і бізнес-правильність роботи потребують окремої перевірки. Живий тест доводить один конкретний сценарій; він не гарантує поведінку всіх версій і конфігурацій CLI.

Початкові діалоги довіри та дозволів необхідно завершити перед робочим обміном. Ручне введення одночасно з доставкою може змішати текст запитів. Перевірка процесу не визначає семантичну готовність кожного діалогу CLI. Зупинення tmux завершує процеси панелей; незалежні служби CLI керуються самим CLI.

Записи містять текст обміну й лежать у приватному тимчасовому каталозі. Вони зберігаються після `stop` для перевірки та не є постійним архівом. Linux перевірено компілятором; живого Linux-тесту не виконано. Сумісність із мінімальною версією Go 1.22 окремим toolchain не перевірялася.

## Запуск

```sh
./2mux start --agents
```

Введіть завдання в Codex після початкових діалогів. Інструкції агентів уже містять їхні точні команди надсилання. Для діагностики використовуйте `./2mux status` і `./2mux messages`.

## Повторний огляд коду та покращення

Під час повторного огляду відтворено ще чотири проблеми перед виправленням:

| Пріоритет | Відтворена проблема | Реалізоване покращення |
| --- | --- | --- |
| P2 | Шість одночасних перших запусків спричинили п’ять помилок `duplicate session`. Runtime-блокування запуску не охоплювали створення сесії. | Приватне блокування життєвого циклу проєкту серіалізує `start` і `stop` перед пошуком та ініціалізацією, звільняючись перед інтерактивним підключенням. Інтеграція тепер охоплює одночасні перші запуски оболонок і агентів. |
| P2 | `send --queue ""` непомітно переходив до пошуку поточного проєкту; порожнє `--from` також обходило перевірку явного значення. | Порожні значення параметрів send відхиляються до пошуку tmux чи доступу до черги. |
| P2 | Записи черги з невідомим відправником, керівними символами у відправнику чи відсутнім часом створення доходили до функції доставки. | Відправник перевіряється під час додавання в чергу, а метадані відправника/часу — під час читання записів, захищаючи заголовок повідомлення та порядок. |
| P1 | Стороння Node-програма розпізнавалася як pi, якщо шлях до скрипта pi був серед пізніших аргументів чи в параметрі середовища виконання. | Розпізнається фактичний підтримуваний шлях до скрипта або назва процесу pi замість перегляду довільних аргументів. Прямі запуски Node/Bun, символьні лінки pi та `bun run` залишаються покритими. |

Перевірки після виправлень: свіже збирання, `go vet ./...` та `TWOMUX_INTEGRATION=1 TWOMUX_NATIVE_SMOKE=1 go test -race -count=1 -v ./...` пройшли. Нові regression-тести падали на початковій реалізації та пройшли з виправленнями. Інтеграція перевірила шість одночасних запусків оболонок із двома різними `TMPDIR`, очікування stop під час призупиненої ініціалізації, шість одночасних запусків агентів і наявний цикл рев’ю з вісьмома доставками. Блокування життєвого циклу використовує сталий простір `/tmp/2mux-control-UID`. Native smoke розпізнав установлених агентів без запиту моделі. Тести використовують унікальні проєкти та видаляють лише власні control-файли блокувань після завершення команд; сокети tmux і записи повідомлень ізольовано в тимчасових каталогах тестів. Документацію CLI й архітектури узгоджено українською та англійською.

Ці зміни не встановлюють гарантій доставки на рівні моделі та не перевіряють налаштування облікових записів/моделей. Попередні збережені живі квитанції залишаються історичним доказом; повторний огляд не запускав нового завдання моделі.
